## Not yet covered

- **No multi-file run driver.** The package has `parse()` per translation unit and `assemble_analysis_model()`, but no command that loops over a project's units. The per-unit `try`/`except` over `PER_UNIT_FAILURES` belongs in that driver, which does not exist yet. The isolation guarantee holds for any caller that follows this pattern. It is not an end-to-end guarantee of the CLI. (Out of scope for this item by instruction: "do not add a multi-file driver".)
- **Failed units have no digest when their source is missing.** Their `inputs` entry is omitted, and the failure reason records the missing source. Parsed units still require a digest.
- **Warnings on failed units.** A unit that fails with errors keeps its diagnostics, including warnings. The helper does not filter them.
- **Eligibility gate does not consume the inventory yet.** The gate's unmodeled-aspects list ("variadic tails, VLAs, unsupported parameter shapes") is now backed by model facts for the first two families; wiring gate reasons to the inventory is TOOL-PAR-170 follow-up (WP-ANA-06 territory), not this item.

## Design notes

- **Why a failed unit, not an exception.** TOOL-PAR-130 asks for partial results. A raised exception would stop the caller from producing the valid units and their model.
- **Why the catch list is explicit.** Catching `Exception` would make a `KeyError` look like a failed unit. The narrow tuple keeps defects visible (NFR-090).
- **Why the eligibility record has `kind`.** A unit-level record with an empty `function` must not look like a function record to CMP-ATG. `kind` makes the difference explicit.
- **Why only variadic tails and VLAs are recorded.** TOOL-PAR-140 records constructs the analyzer *recognises as unsupported*; the extractor's own recognition list (the eligibility gate's unmodeled-aspects note) names exactly these two families, and both have a precise machine check (`type.is_function_variadic()`, `TypeKind.VARIABLEARRAY`/`DEPENDENTSIZEDARRAY`). "Unsupported parameter shapes" has no concrete recognition point in the extractor yet and is left unpopulated rather than invented. Prototypes without definitions and non-main-file declarations are by-design scope exclusions (external declarations), not unsupported constructs, and are not recorded.
- **Why `location` is the owning definition.** The first occurrence's precise location follows the deterministic walk order; `detail` names the function or `function.parameter`, so the entry stays machine-checkable without embedding absolute paths.
