## 2. Findings

### F-01 — BuildContext vs WP-ING-01 ingestion: core aligned, four required dimensions missing
**Class:** gap

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 `BuildContext` (lines 98–104): store "original compile command and a parsed argument array; working directory; source identity; compiler binary/version; target triple/ABI; language/standard; include search order; defines/undefines; response-file contents and identity; SDK/sysroot identity; and relevant explicitly selected environment values"; "Multiple commands for one source file are distinct configurations"; "Reject unresolved command parsing and unsupported flags instead of silently deleting them." DEEP_ANALYSIS.md boundary 1 (lines 33–37) derives the same field set from D5/D13 and adds "Preserve the original command even when an adapter derives a separate analysis command."

**ectt baseline evidence:** SRS-001:122–128 (TOOL-ING-010..030) requires accepting `compile_commands.json`, parsing `command`/`arguments` forms, and extracting "source path, working directory, include paths, preprocessor definitions, language standard, and compiler invocation" — allocated to WP-ING-01 (PLAN-001:253, 343). Implemented `src/ectt/ing/model.py`: `CompilerInvocation` carries `executable`, `arguments` (full normalized vector — original command preserved), `residual_flags` (unsupported flags retained, not deleted); `TranslationUnit` carries `working_directory`, `include_paths`, `preprocessor_definitions`, `language_standard`, `output_file`; `CompilationDatabase.filter_by_source()` (model.py:151–154) returns *all* entries for a path, so multiple configurations per file are representable. `src/ectt/ing/compdb_adapter.py:43–105` parses both `command` strings and `arguments` arrays and raises `CommandParseError` on unresolvable quoting (adapter:77–91), matching "reject, don't silently delete".

**Assessment:** The implemented ing model captures 6 of the 10 BuildContext dimensions: original command, parsed arguments, working directory, source identity, include order, defines, language standard. Missing: (a) **compiler version** — only the executable string is kept; the version in S1 provenance (`persist.py:114–117`) is the *libclang analysis* version, not the build compiler's; (b) **target triple/ABI** — nowhere in the ing model; (c) **response files** — `parse_command_to_arguments` performs no `@file` expansion or content/identity capture (verified: no `response`/`@`/`sysroot` matches in `src/ectt/`); (d) **SDK/sysroot identity and selected environment values** — absent. Also note `CompilationDatabase.get()` returns the *first* match only (model.py:143–149); downstream consumers must be careful to use `filter_by_source` or multi-configuration identity is lost.

**Recommendation:** Treat these as candidate additions to TOOL-ING-030 (a minor, additive extension consistent with SDD-002 §3's versioning rule) or a new requirement under a future ING revision. Response-file expansion is the most urgent of the four: it silently changes what a "recorded flag set" means. Do not claim BuildContext parity in any design doc until (a)–(d) are allocated.

### F-02 — AnalysisSnapshot vs S1: field semantics genuinely match
**Class:** aligned

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 `AnalysisSnapshot` (lines 106–110): failed/unsupported TUs "remain in the declared scope with their status and reason"; "Their number of coverable entities is unknown until a valid mapping exists; do not invent a denominator"; unsupported constructs recorded; indirect calls remain unresolved where evidence is insufficient.

**ectt baseline evidence:** SDD-002 §4.2 (line 144): "A failed unit appears with `status: \"failed\"` and diagnostics — an incomplete model must be visibly incomplete (DSN-ANA-090)." Implemented: `src/ectt/ana/persist.py:119–169` converts failed or error-bearing parses into `AnalysisUnit(status=\"failed\", diagnostics=..., functions=(), types={})` — the unit stays in the model with its reason (diagnostics) and contributes *nothing* to any denominator (there are no denominators in S1 at all). `analysis-model-1.0.schema.json:73–79` enumerates `status: parsed|failed`. The schema (lines 246–273, 298–318) permits `calls[].via: \"function_pointer\"` and free-form `annotations`, matching "indirect calls remain unresolved" and "unsupported constructs recorded". `persist.py:303–240` enforces transitive type closure on assemble and again on read (persist.py:366–383), which the proposal's "stub must compile standalone" need also implies (SDD-002 §4.2 line 141, TOOL-STB-030).

**Assessment:** Semantic alignment is real, not superficial: both sides refuse to let a failed unit masquerade as an empty-but-complete one, and neither invents coverage denominators at the analysis layer. One structural difference: the proposal keys the snapshot on a "source/build-context digest"; ectt's S1 provenance carries per-input file digests (`persist.py:207–226`) but no compilation-database/configuration digest — the SDD-003 §9 cache key ("compilation database entry, source digests, flags, front-end version") covers it at the cache layer instead. Acceptable, but the binding between an S1 model and the BuildContext that produced it is currently implicit.

**Recommendation:** No design change needed. When S1 gains build-context identity (see F-01), record it in `provenance` as an additive minor version.

### F-03 — S1's decision inventory and annotations are specified but not yet emitted by the implemented model
**Class:** risk

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 AnalysisSnapshot (line 108) requires "unsupported constructs" to be recorded, and DEEP_ANALYSIS.md boundary 6 (lines 63–67) requires "artifact completeness" kept independently — both depend on a machine-readable inventory of what analysis could and could not account for.

**ectt baseline evidence:** SDD-002 §4.2 (lines 145–146) makes two obligations load-bearing: "Unhandled constructs recorded as `annotations`, never omitted" and "`decisions[]` is emitted whether or not coverage runs", the latter being the input to DSN-COV-040's reconciliation. The implemented `src/ectt/ana/model.py` `FunctionModel` (lines 245–285) has fields only for name/linkage/storage_class/location/return_type/parameters/globals — **no `calls`, `decisions`, `complexity`, or `annotations`** are produced. The published schema declares them optional (schema lines 246–318), so documents currently validate, but the DSN-COV-040 reconciliation contract has nothing to reconcile against yet.

**Assessment:** This is a known implementation-lag situation, not a design conflict — but it is the single point where the vcast proposal's AnalysisSnapshot contract would silently *appear* satisfied (schema-valid documents) while the decision-inventory guarantee that makes S4's "unmeasured ≠ uncovered" check possible is absent. The proposal's boundary 6 ("coverage cannot stand in for a correctness oracle") inherits exactly this dependency.

**Recommendation:** Track as implementation debt against SDD-002 §4.2; add an acceptance fixture that fails if a model document contains a function with decisions-bearing code but an empty `decisions` array. Do not use the schema alone as evidence of S1 conformance.

### F-04 — HostProfile (target→host derivation record with ABI differences) has no counterpart anywhere in ectt
**Class:** gap

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 `HostProfile and LinkPlan` (lines 112–114): "An embedded production command is not automatically a valid host command... Any derivation from a target build needs a versioned HostProfile recording target/host triples, flag changes, defines, substituted platform headers and unavailable hardware behavior. Record known ABI differences such as widths, alignment, packing, endianness and signedness; leave unmeasured differences unknown... label every result with its execution profile. Host success does not establish target behavior."

**ectt baseline evidence:** Searched SRS-001, SDD-002, SDD-003, and `design/trace/design-elements.yaml` for ABI / host profile / derivation: there is **no occurrence of "ABI" in SRS-001** (grep verified) and no HostProfile concept in the seam register or data model. The closest baselines are TOOL-TCH-010/050 (SRS-001:194, 202 — per-compiler configurations) and TOOL-TGT-070 (SRS-001:372): "Test cases shall execute unmodified on host and target, with only configuration distinguishing the two." SDD-002 §3's `execution` metadata (`where`, `toolchain`, `target_id`, SDD-002:226–227) labels *where* a run happened, not *how the host configuration was derived from the target one* or *which ABI differences it carries*.

**Assessment:** Genuine gap. Note the subtle tension: TOOL-TGT-070 asserts host/target equivalence "with only configuration distinguishing the two", while the proposal's premise is that host/target equivalence must be *established and recorded* (derivation record + layout probes), with unmeasured differences staying unknown. These can coexist — ectt's compiler-configuration extension point (SDD-002 §10, line 497) plus S7's conformance-test obligation (TOOL-TCH-060) is the natural home — but ectt currently has no required artifact that records ABI deltas or declares them unknown.

**Recommendation:** If embedded-target support (P3, WP-BLD-03/TGT) proceeds, allocate a HostProfile-equivalent design element before TOOL-TGT-070's acceptance testing, or TOOL-TGT-070 will be interpreted as claiming equivalence by default — precisely the overclaim the proposal warns against.

### F-05 — LinkPlan: pre-build link validation exists in the design; an explicit link manifest does not
**Class:** gap (partial coverage)

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 (lines 114–116): "each EnvironmentRevision also requires a validated LinkPlan. The initial explicit manifest names selected objects, ordered libraries/archives, search paths, resolved library identities, linker flags/response files, runtime choice, entry point and linker identity... a future build-system adapter may generate this manifest, but `compile_commands.json alone is insufficient`. An unresolved input blocks building rather than being guessed." FR-01 (line 231) makes "an explicit validated LinkPlan" a first-release requirement with acceptance evidence including "missing link inputs".

**ectt baseline evidence:** `src/ectt/ing` confirmed free of any link concept — `CompilationDatabase`/`TranslationUnit`/`CompilerInvocation` (model.py) carry compile-time data only; grep for library/link/manifest terms in `src/ectt/ing/*` returns nothing. At the design level, TOOL-HAR-120 (SRS-001:242) requires resolving "all undefined external references in the harness link step, either by stub generation or by explicit user-supplied linkage, and shall report any that remain unresolved", discharged by DSN-GEN-090 (design/trace/design-elements.yaml ~731–741): "Before building, the undefined-symbol set of the harness is computed and resolved from three sources... Anything left over is reported by name... rather than emerging as a linker error." PLAN-001:372 packages this as WP-GEN-05 "Link closure and unresolved reference reporting". No PLAN-001 work package or SRS requirement names an ordered link manifest, resolved library identities, linker identity, or entry point.

**Assessment:** Overlap is real but partial. DSN-GEN-090 is *computed* closure over the harness's undefined symbols with a fixed three-source resolution policy; the proposal's LinkPlan is an *authored, validated manifest* of ordered inputs with identities, which also covers inputs symbol closure cannot see (library order, archive member selection, runtime choice, entry point — exactly the cases in the proposal's §4 where "the requested partial replacement is unsupported unless the build can select the required objects independently"). Ectt's DSN-GEN-130 ("the tool does not attempt `-nostdlib` or link-order tricks") shows the register is aware of link-order sensitivity but deliberately declines to manage it.

**Recommendation:** Classify as a genuine new concept. If adopted, it belongs as a new design element under CMP-GEN/CMP-BLD (or a new seam if it becomes user-authored input, since authored persisted state falls under SDD-002 §3 / SDD-003 §5 policy). Minimal viable reconciliation: require the LinkPlan manifest to carry a digest bound into the generated artifact (extending SDD-003 §7's digest-bound record table, which currently binds generated artifacts only to the *analysis model* digest, TOOL-HAR-110).

### F-06 — EnvironmentSpec/EnvironmentRevision: recipe contents match; immutable-revision semantics do not exist yet
**Class:** gap

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 (lines 118–124): "An environment is an immutable recipe: UUT selection, dependency choices, type-data schema, harness/test-framework version, instrumentation backend/options, compiler and execution target"; "A recipe change creates a new build identity and invalidates affected results" (DEEP_ANALYSIS.md boundary 2, line 43).

**ectt baseline evidence:** SDD-003 §2.1 (lines 92–94) authors one file per environment (`adc.host.env`, `adc.target.env`) in the version-controlled project tree; the SRS glossary (SRS-001:939) defines Environment as "A built, executable configuration comprising a test scope, its harness, its stubs, and its toolchain settings"; TOOL-UIX-070 (SRS-001:542) collects the same recipe dimensions at creation (scope, compiler configuration, target, coverage kind, framework back-end); SDD-002 §9.2 (line 422) shows `environment.build` as an S6 operation. For identity, SDD-003 §6 (line 256): "Environment id — derived from scope + toolchain + target — stable across Rebuild."

**Assessment:** The recipe *contents* align almost one-for-one (dependency choices appear as S2 `stubs` plus DSN-GEN-130 per-function opt-out and TOOL-UIX-180's per-environment stub view). What is missing is the **revision semantics**: ectt environment files are mutable authored state whose id survives rebuilds, and no contract invalidates *results* when an environment recipe changes. SDD-003 §7's digest-bound records bind generated artifacts to the *analysis model* digest (TOOL-HAR-110) and test cases to the *interface* digest (TOOL-CBT-070) — there is no digest binding an artifact or a result set to the *environment recipe* that produced it. The proposal's core claim ("recipe change → new build identity → results invalidated") has no ectt equivalent; the closest is the generic S5 provenance `build_id` (SDD-002:358), which is undefined in SDD-002/SDD-003.

**Recommendation:** Two candidate allocations, both additive: (a) extend SDD-003 §7's digest table with an "environment recipe → build/result identity" row; (b) define `build_id` in SDD-002 §8/S5 provenance as a function of (recipe digest, toolchain identity, generated inputs). Until then, S3 consumers cannot distinguish results from two different builds of the same environment id.

### F-07 — BuildArtifact + CompiledTestManifest: executable↔test-binding gate is absent
**Class:** gap

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 (lines 120–126): build produces "a separate immutable artifact with executable digest, generated-source manifest, source mapping, build command/diagnostics and coverage mapping identity"; "BuildArtifact retains a CompiledTestManifest mapping executable case selectors to exact TestRevision identities and generated-source digests. Execution rejects a mismatched test revision." §7 ER model (lines 206–211) makes the binding table mandatory ("BUILD_ARTIFACT ||--|{ COMPILED_TEST_BINDING") and the artifact reference "mandatory before execution". FR-03 (line 233): "mismatch is rejected, historical records persist".

**ectt baseline evidence:** SDD-003 §2.1 (line 116) reserves `build/` for "objects, binaries, per toolchain" in the output tree, and §7 (line 283) binds a generated artifact to the digest of the analysis model it came from, with mismatch marking it *stale* (TOOL-HAR-110, SRS-001:240). S3's result set (SDD-002:222–237) carries no executable digest or artifact identity; the only run-to-build linkage offered anywhere is S5 provenance `build_id` (SDD-002:358). No SRS requirement, work package, or design element requires verifying, at execution time, that the selected test cases are the ones compiled into the binary about to run.

**Assessment:** Ectt has artifact *staleness detection*; the proposal requires artifact→test *binding enforcement* (a gate, not a marker). These are different guarantees: a stale marker can be displayed and ignored; a mismatch gate prevents a run whose binary contains different compiled test content from producing results attributed to those test ids. Given ectt's S2 design (values may be edited while id stays stable, SDD-002 §5.1), the failure mode the proposal targets — running a stale binary and attributing results to the current case content — is reachable in ectt's model via test case→interface staleness (TOOL-CBT-070) only for *interface* changes, not for edits to the case's own inputs/expected values.

**Recommendation:** Allocate. The cheapest ectt-native shape: extend the S3 run header with an `artifact` reference (digest + generated-input digests) required for `execute` operations, and extend SDD-003 §7 with a compiled-test binding row. This also gives `build_id` (F-06) a concrete definition.

### F-08 — TestSpec vs S2: identity, origin, requirement links, and comparison policy align
**Class:** aligned

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 `TestSpec and oracle` (lines 128–132): "Keep stable test identity and revision separate from run history. A test stores requirement links, selected function, inputs, preconditions, explicitly writable globals, expected return/output/global values, stub behavior, timeout and comparison policy"; "generated input that increases coverage is not proof of correctness"; "Floating-point tolerances... must be declared rather than guessed."

**ectt baseline evidence:** SDD-002 §5 (lines 166–206): id "assigned at creation, never derived (DSN-TCM-110)" (line 169); the case carries `requirements`, `inputs` (parameters + globals), `expected` (return, globals, out_parameters, per-field `comparison` incl. float `tolerance`), and `stubs` with sequences/expect_calls/out_parameters — every content element of the proposal's TestSpec is present in the S2 model, plus `origin` (human/atg/ai + review state) which generalizes the proposal's "user-reviewed ... suggestions remain unreviewed until accepted" via TOOL-ATG-080 and the S5 `unreviewed_expectations` advisory (SDD-002:364). TOOL-TCD-140 (SRS-001:306) and SDD-003 §6 (line 254) pin identity stability across edits/regeneration/moves.

**Assessment:** Aligned, with ectt strictly ahead on two points the proposal handles elsewhere or omits: type-directed comparison is *defined by C type from S1 with explicit overrides* in ectt (SDD-002 §5.1, DSN-TCM-030), whereas the proposal leaves comparison policy as test-local data; and ectt's single model for `data` and `c_source` kinds (SDD-002 §5.1) matches the proposal's "multiple authoring experiences with common execution and result contracts" (DEEP_ANALYSIS boundary 3). The one proposal element S2 does not carry is an explicit per-test `timeout` field — ectt's S3/TOOL-EXE-040 treat timeout as a runner configuration; where the timeout value lives is unspecified in both. Residual difference (revision identity of the test itself) is deferred to F-07/F-10 rather than double-counted here.

**Recommendation:** No action for S2 itself. Decide where per-test timeout configuration lives before TOOL-EXE-040 acceptance (S2 optional field vs environment configuration).

### F-09 — RunRecord vs S3: timeout/partial/infrastructure semantics match; the three-dimension split only partially maps
**Class:** aligned

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 `RunRecord` (lines 134–144): "Only completed runs with evaluated passing assertions may be reported as test passes"; "A timeout is never converted into an assertion failure or a pass"; coverage/artifacts dimension "complete, partial, unavailable, incompatible"; "Preserve any partial logs/profiles after a crash"; infrastructure-error is an execution state.

**ectt baseline evidence:** SDD-002 §6.1 (lines 239–248): "`partial` and `not_executed` are **fields, not report options** — a subset run cannot be presented as a full one because the flag travels with the data (TOOL-CBT-040, DSN-CBT-030)"; "`infrastructure_faults` is a separate channel from `results`. A rig that fails to flash must never read as failing software (TOOL-TGT-090)"; "`timeout` is a distinct outcome from `fail`, since the diagnosis differs"; "`order_seed` is recorded so a randomised-order failure is reproducible." The S3 outcome enum (SDD-002:230) includes `timeout` and `not_run` beside `pass|fail|error`.

**Assessment:** The safety-critical semantics the proposal enumerates are already contract points in S3, in nearly identical language: partial-run disclosure, infrastructure-vs-test separation, timeout distinctness, and reproducibility metadata (order_seed). Two of the proposal's three RunRecord dimensions map cleanly: *execution* → S3 `execution` + `outcome` + `infrastructure_faults`; *coverage/artifacts* → S4's own completeness vocabulary (`unmeasured`, §7.1) plus S3 `partial`. The third — an explicit *oracle* dimension with its own evaluation record — does not exist in S3 (see F-10).

**Recommendation:** None for the aligned core; it is a strength of the baseline. Use these S3 contract points verbatim when responding to the proposal.

### F-10 — RunAttempt identity and the oracle/artifact dimensions of RunRecord are new
**Class:** gap

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 RunRecord (line 144): "Allocate a unique RunAttempt before building, bound to TestRevision and EnvironmentRevision. Attach a BuildAttempt and diagnostics; BuildArtifact is absent until a build succeeds. Execution requires an exact finalized artifact and matching CompiledTestManifest. Repeated identical tests still have separate attempt identities. An OracleEvaluation records execution evidence, expectation revision, comparison policy and evaluator version. Later reevaluation creates another record rather than rewriting historical results." §7 ER model (lines 208–216) encodes the attempt/build/oracle/coverage separation.

**ectt baseline evidence:** S3 (SDD-002:222–237) keys results by `test_id` within a `run_id`; nothing in SRS-001, PLAN-001, SDD-002, or SDD-003 defines an attempt identity allocated *before* build, a build-attempt sub-record, or an evaluator-versioned oracle record (grep for "attempt" across SRS-001 and PLAN-001 finds no relevant requirement; PLAN-001:282 WP-CORE-01's "two runs from identical inputs produce byte-identical artifacts" is determinism, not attempt identity). Historical re-evaluation is supported only indirectly: CMP-CBT "reads *persisted* result sets from the store" (SDD-002:214–216) so old sets survive, but there is no contract that a *re-evaluation* produces a new record rather than mutating.

**Assessment:** Genuine gap, but its weight depends on scope: for v1.0's host MVP the run_id/persisted-store combination approximates attempt identity; the proposal's full value appears where builds can fail *after* an attempt exists, artifacts are cached and reused, and oracles are re-evaluated — i.e., WP-BLD-01 incremental rebuild plus any future ATG loop (DSN-ATG-110's `build → execute → measure` port would consume exactly these identities). Notably, the P1 TestValidationPort signature (`build(test_cases) -> build outcome + diagnostics`, SDD-002:631–634) already implies build-failure-without-artifact as a first-class outcome, but no data contract carries it.

**Recommendation:** Defer full RunAttempt to the BLD/EXH design stage, but reserve the identity scheme now (one sentence in SDD-003 §6's identifier table: "Run attempt id — allocated before build — lifetime of evidence"). Retrofitting identity formats after results exist is the TOOL-PRJ-030 anti-pattern SDD-003 §1 warns about.

### F-11 — TOOL-EXE-040 says timeouts "report as failures"; SDD-002 and the proposal both require timeout to be distinct
**Class:** conflict

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 RunRecord (line 142): "A timeout is never converted into an assertion failure or a pass." §6 (line 190): "Record observed outcomes without guessing a hidden crash from timeout alone."

**ectt baseline evidence:** SDD-002 §6.1 (line 246): "`timeout` is a distinct outcome from `fail`, since the diagnosis differs"; S3 outcome enum (line 230) includes `timeout`. SRS-001:344, TOOL-EXE-040: "The tool shall enforce a configurable per-test timeout and **report timed-out tests as failures**."

**Assessment:** Internal baseline conflict surfaced by the comparison: the requirement text and the interface design disagree on the exact point both this proposal and DEEP boundary 6 treat as a correctness-critical invariant (a timeout may indicate a hang, an infinite loop, or an environment stall — collapsing it into `fail` destroys the diagnosis and, worse, invites "failed because slow" misreads in reports). SDD-002 is the deliberate, argued position (its contract-point table gives the reason); TOOL-EXE-040 reads like loose phrasing rather than a contrary decision, but under SDD-004 §3 the register/SRS is authoritative until changed, so the conflict is real on paper.

**Recommendation:** File an SRS change request against TOOL-EXE-040 (SRS §30: materially changed requirement gets a new id; old marked superseded) to read "report timed-out tests with a distinct timeout outcome, never as an assertion failure" — matching SDD-002 §6.1. Until then, implementation should follow SDD-002 and record the deviation.

### F-12 — CoverageSnapshot vs S4: unmeasured ≠ uncovered, form-as-data, attribution and merge all align
**Class:** aligned

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 `CoverageSnapshot` (lines 146–154): "A missing TU mapping means completeness is unknown, not zero coverable entities. Never label a measured-subset percentage as complete project coverage. Distinguish mapped zero hits from missing profiles"; "Keep backend metrics named accurately"; "record which run outcomes contribute to each aggregate"; per-test profiles imported before aggregates (lines 152–154); FR-07 (line 237): "failed TU and missing profile never yield unqualified project-wide 100%".

**ectt baseline evidence:** SDD-002 §7.2 (lines 324–327): "`unmeasured` is not `uncovered`. A decision the compiler declined to instrument is a third state. Collapsing it into either of the other two is the most dangerous misreport the tool can make (DSN-COV-040)." `mcdc.form` is data rendered by every renderer (lines 321–323, TOOL-COV-060 SRS-001:398 names the "compiler mechanism"); S4 `files[].role` separates uut/harness/stub/framework coverage (TOOL-COV-160); `attributed_tests` (lines 331–334) implements TOOL-COV-120 per-test attribution; §7.1 (lines 303–313) defines the merge contract (identical source/condition mapping/configuration, union outcome flags, never OR into independence) matching TOOL-COV-110; `justified` records expire on source-digest mismatch (TOOL-COV-150). SRS-001:402 (TOOL-COV-080) requires non-instrumentable expressions be detected *and reported* — the ectt mechanism is exactly the analyzer-inventory-vs-coverage reconciliation the proposal's "unsupported constructs remain visible" implies.

**Assessment:** The proposal's CoverageSnapshot semantics are, with one exception (F-15: provider/version identity and executable/profile binding), a subset of S4's contract points. Ectt additionally specifies the denominator discipline (demonstrated / all in-scope inventory, optional measured-only denominator explicitly labeled, zero denominator N/A — SDD-002 §7.1 lines 293–299) which is the same "no invented denominators" rule the proposal applies to missing mappings.

**Recommendation:** None. When importing the proposal's "contributing runs per aggregate" idea, S4's per-record `attributed_tests` plus S5 run provenance is the natural carrier — keep it additive.

### F-13 — Function-eligibility/observability gate is a new contract absent from ectt
**Class:** gap

**vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §1 (lines 31–37): a detailed eligibility contract — "externally linked, non-variadic C functions whose declarations are available through headers"; supported input/output types enumerated; "The parser may discover more than the generator can test; discovery must not imply eligibility"; "Every specified precondition and expectation must be observable through parameters, return values, supported buffers, accessible external objects, public API calls or stub records... the tool cannot offer arbitrary reads/writes of file-scope or function-local statics. Report inaccessible requested state explicitly." §4 (lines 162–168) extends the gate to stubbing: same-TU calls, internal linkage, inlining "does not cover"; reject unsupported ABI attributes; verify replacement with linker-map evidence.

**ectt baseline evidence:** Ectt's neighboring contracts: S1 `annotations` for unhandled constructs (SDD-002:145), DSN-GEN-150 unhandled-construct marking (design-elements.yaml ~795 ff.), DSN-GEN-130 selective stubbing with declared per-toolchain capability and refusal where undeclared, DSN-GEN-140 same-TU interception via `--wrap` "refused rather than approximated" where the toolchain lacks it, and the S7 rule that a compiler configuration claiming a capability it cannot deliver fails conformance (SDD-002:515–519, TOOL-TCH-060). S1 records linkage/storage_class per function (schema lines 137–163), so the *inputs* to an eligibility decision exist. But no SRS requirement, design element, or seam defines an eligibility/observability gate as a contract — nothing requires that "discovery must not imply eligibility" or that inaccessible requested state be reported as such (grep across SRS-001: no "eligib", no observability-gate requirement; TOOL-PAR-030..050 cover extraction, not testability classification).

**Assessment:** Genuine new concept, and arguably the most valuable import from the proposal for ectt's ATG story: ATG generation (CMP-ATG, DSN-ATG-110) currently has no contract telling it which S1 functions it may target. The ectt-native shape is an S1-adjacent classification (data, not code): per-function eligibility with typed reasons, carried as an additive S1 minor or as a projection consumed by CMP-ATG/CMP-GEN, with the observability rule (no arbitrary static reads; report inaccessible state) as its own requirement under ATG or GEN.

**Recommendation:** Allocate after the S1 decision-inventory debt (F-03) is cleared — eligibility is computed from exactly those S1 fields. Keep it declarative per SDD-002 §10's extension-point philosophy so per-compiler capability data can participate.

### F-14 — D5 (shipped Clang adapter configures parser separately from build compiler) supports S1's front-end exclusivity rule
**Class:** aligned

**vcast-findings evidence:** DEEP_ANALYSIS.md evidence register D5 (line 19): "`../selected/Compilers/Clang/Clang.py`, lines 72–155 — Separate preprocessing, compile, link and EDG parser option construction. Compiler identity and language mode influence commands." Boundary 1 (line 35): "The parser and the build compiler are separately configured." Verified in the artifact itself: `vcast-findings/selected/Compilers/Clang/Clang.py` — `constructPreprocessCommand` (lines 72–88), `constructCompileCommand` (lines 89–105, emitting `C_COMPILE_CMD` and `C_COMPILER_VERSION_CMD`), `constructLinkCommand` (lines 106–115), and `constructEDGflags` (lines 117–158, emitting `C_EDG_FLAGS` with `--clang_version` pins): four independently constructed option sets, with the EDG analysis-parser flags derived from but distinct from the build compile command.

**ectt baseline evidence:** SDD-002 §4 (lines 98–102): "**The rule that gives it force:** no component outside `CMP-ANA` may link, import, or invoke a C front-end. Not 'should not' — the dependency is absent from every other component's manifest, so a violation fails the build rather than review." Implemented: `src/ectt/ana/frontend.py` module docstring — "Owns the sole libclang dependency in ectt per SDD-001 S4.2 and SDD-005 S5.3" — with `LIBCLANG_FLOOR_VERSION (18, 1)` (frontend.py:46) and a version-gate error path (frontend.py:180–182); `src/ectt/ing` contains no front-end import (its model/adapter are pure data parsing).

**Assessment:** D5 is independent industry evidence *for* the ectt rule's premise: the commercial reference architecture also keeps the analysis parser separately configured from the build compiler, so analysis semantics never silently track build-tool identity. Ectt goes further than the observed VectorCAST mechanism: where VectorCAST's adapter *constructs* separate option sets inside one compiler adapter, ectt makes the front-end dependency structurally impossible outside CMP-ANA. The D5 observation therefore supports, and does not tension with, S1. One honest asymmetry to note: SDD-002 §3 AnalysisSnapshot's caveat "Do not treat a Clang parse of a vendor dialect as proof of target-compiler equivalence" (PRODUCT_ARCHITECTURE line 110) has its ectt analogue in S7's conformance-test obligation (TOOL-TCH-060), not in an S1 field — the declaration lives at the extension point.

**Recommendation:** Cite D5 as supporting evidence (not as a requirement source) if SDD-002 §4's rationale is ever revisited; the DEEP_ANALYSIS boundary line is quotable as third-party practice.

### F-15 — Consolidated register of genuinely new concepts absent from SDD-002/SDD-003
**Class:** gap

**vcast-findings evidence (per concept):**
1. **LinkPlan remainder** — explicit ordered manifest, resolved library identities, linker identity, entry point (PRODUCT_ARCHITECTURE:114–116). Ectt has only computed symbol closure (DSN-GEN-090; F-05).
2. **HostProfile** — versioned target→host derivation with ABI deltas, unmeasured differences left unknown (PRODUCT_ARCHITECTURE:112–114). Absent everywhere (F-04).
3. **CompiledTestManifest** — executable↔TestRevision binding, rejection gate before every run (PRODUCT_ARCHITECTURE:126, §7 lines 206–211). Absent (F-07).
4. **Function-eligibility/observability gate** — discovery ≠ eligibility; observability through declared channels only; inaccessible state reported (PRODUCT_ARCHITECTURE:31–37). Absent (F-13).
5. **Per-test profile import + fresh-process-per-test with unique profile path** — one fresh process per test, unique profile path, per-test profile imported before aggregates, "assume no usable profile after a crash unless collected and validated", accept only from owned run directory (PRODUCT_ARCHITECTURE:152–156). Ectt has the *attribution* contract (S4 `attributed_tests`, TOOL-COV-120) and isolation intent (TOOL-EXE-030 SRS-001:342), but no process/profile mechanics contract; TOOL-EXE-030 does not specify process-per-test.
6. **RunAttempt/BuildAttempt/OracleEvaluation identities** (PRODUCT_ARCHITECTURE:144). Absent (F-10).
7. **EnvironmentRevision immutability semantics** — recipe change invalidates results (PRODUCT_ARCHITECTURE:118–124; DEEP boundary 2 line 43). Absent (F-06).
8. **Resolution-freshness cache invalidation** — validate include/library resolution still selects same inputs; `__has_include` changes, shadowing headers, library replacement invalidate without any previously consumed file changing (PRODUCT_ARCHITECTURE:122–124). SDD-003 §9 (lines 360–368) keys the cache on "compilation database entry, source digests, flags, front-end version" — a content key that misses resolution-order effects.
9. **Coverage provider version identity + executable/profile binding** — snapshot retains provider+version, and "a raw profile is meaningful only with the matching executable/mapping" (PRODUCT_ARCHITECTURE:148–154). S4 names the MC/DC mechanism (SDD-002:260–262) but has no general provider/version field and no executable-digest binding.
10. **Analysis-argument transformation record** — "Keep analysis arguments separate from production-build arguments with an explained transformation record" (PRODUCT_ARCHITECTURE:100). Ectt preserves the original argument vector (`ing/model.py:34–35`) but the ClangFrontend's flag translation is internal and unrecorded.

**ectt baseline evidence (collectively):** SDD-002 §2 seam register (lines 39–53) contains no seam or port for build/link/artifact identity; SDD-003 §6 identifier table (lines 252–258) defines five identifiers, none of which is an attempt, artifact-binding, or recipe-revision id; SDD-003 §7 digest table (lines 280–286) binds four record types, none to an environment recipe, executable, or link manifest; PLAN-001's 183 work packages (PLAN-001:230 "Total 183") contain no work package for a link manifest, host profile, or compiled-test binding (WP-GEN-05's link closure is the sole link-related package, PLAN-001:372).

**Assessment:** All ten items are genuinely absent; none is a renaming of an existing ectt concept. Ranked by blast radius if unadopted: (3) CompiledTestManifest and (7) EnvironmentRevision — silently wrong attribution of results to builds; (2) HostProfile — silently wrong equivalence claims for target work; (8) resolution-freshness — stale caches that pass content checks; the rest are containment/mechanics with clearer local failure modes. Also worth stating: several of these (LinkPlan remainder, HostProfile, RunAttempt) are P3-adjacent given ectt's phasing (host MVP first, TOOL-TGT at P3), so adoption timing, not adoption itself, is the live decision.

**Recommendation:** Route this list into the SRS/PLAN change-control flow (SDD-004 §7) as candidate requirements with the proposal sections as external rationale. Do not fold them silently into existing requirements; each needs its own id so the trace gate can hold it. Items 3, 7, and 8 are the ones I would allocate before WP-BLD-01/WP-EXH-01 acceptance; items 1, 2, 5 can wait for the P3 target phase; 4 belongs with CMP-ATG design; 6, 9, 10 are small additive schema/identity decisions.

## 3. Summary

- **The seven-seam structure absorbs the proposal well.** 5 of 10 mapped contracts are aligned with S1–S4/S2 semantics at the contract-point level (failed-TU visibility, no invented denominators, timeout/partial/infrastructure discipline, unmeasured ≠ uncovered, assigned test identity, MC/DC form as data, merge contract). The proposal's safety semantics and ectt's SDD-002 contract points are near-verbatim on the points that matter most.
- **The gaps cluster in one place: build/execution identity.** Ectt specifies *what evidence means* (S1/S3/S4) but not the identity chain that binds a result to the exact recipe→artifact→compiled-test revision that produced it (EnvironmentRevision F-06, BuildArtifact/CompiledTestManifest F-07, RunAttempt F-10). This is the proposal's §3/§7 backbone and ectt's largest structural blind spot.
- **One internal conflict surfaced:** SRS-001 TOOL-EXE-040 ("report timed-out tests as failures", SRS-001:344) contradicts SDD-002 §6.1's timeout-distinctness (SDD-002:246) and the proposal's RunRecord invariant. Needs an SRS change request before EXE acceptance testing.
- **Two implementation debts could fake conformance:** the S1 model does not yet emit `decisions[]`/`annotations` though the schema permits their absence (F-03), and the ing model lacks compiler version, target/ABI, response files, and SDK identity though the schema/requirements never demanded them (F-01). Schema-valid ≠ contract-complete.
- **D5 independently corroborates S1's front-end exclusivity** (F-14): VectorCAST's own shipped adapter constructs EDG parser options separately from build compile/link commands (`Clang.py:72–158`), the same premise SDD-002 §4 enforces structurally (SDD-002:98–102; `ana/frontend.py` sole-libclang).
- **Counts:** aligned 5 (F-02, F-08, F-09, F-12, F-14) · conflict 1 (F-11) · gap 8 (F-01, F-04, F-05, F-06, F-07, F-10, F-13, F-15) · risk 1 (F-03). Total 15.
