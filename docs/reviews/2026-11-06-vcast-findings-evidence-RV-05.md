## Findings

### F-01 — No requirement or WP exists for an explicit validated link plan (Class: gap)
- **vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 "HostProfile and LinkPlan": "each EnvironmentRevision also requires a validated LinkPlan. The initial explicit manifest names selected objects, ordered libraries/archives, search paths, resolved library identities, linker flags/response files, runtime choice, entry point and linker identity … An unresolved input blocks building rather than being guessed"; FR-01 acceptance evidence lists "missing link inputs". P02 acceptance: "A missing library or ambiguous object blocks the build with a diagnostic."
- **ectt baseline evidence:** SRS-001 §6 TOOL-HAR-120 only requires resolving undefined external references and reporting unresolved ones (WP-GEN-05, L2 P2, unimplemented — PLAN-001 line 372); grep of PLAN-001 for "link" yields only WP-GEN-05/WP-TRC/WP-AIF rows; SDD-003 §8 stores "linker files, libraries" only inside archived verification records; PLAN §7.1 proves 100% SRS allocation, so nothing is hiding in the register.
- **Assessment:** The compile-side import (FR-01 first half) is implemented (WP-ING-01), but the link-manifest concept — an authored, validated artifact with resolved inputs and linker/runtime identity that gates the build — is absent from SRS-001, PLAN-001 and the SDD seams. Ectt implicitly delegates link correctness to the harness link step (HAR-120) at generation time, which reports failures but never *pre-validates* an explicit plan.
- **Recommendation:** Treat P02/FR-01(link half) as a candidate new requirement pair (e.g. a TOOL-BLD/TOOL-ING extension: "authored environment link manifest, validated before build; unresolved input is a blocking diagnostic") plus a WP in CMP-BLD/CMP-GEN. Decide deliberately whether ectt's HAR-120 post-hoc reporting is an acceptable substitute before porting the concept.

### F-02 — Stub symbol-resolution proof is required by vcast-findings but absent from SRS/PLAN (Class: gap)
- **vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §4: "Use object/archive symbol information and retained linker-map or equivalent resolution evidence to verify that each replaced symbol resolves to the generated stub and the original object is absent … Reject archive-member substitutions where replacement ownership cannot be established." P06: "Link map confirms the selected stub; conflicting or mixed object ownership is rejected."
- **ectt baseline evidence:** SRS-001 §7 TOOL-STB-010–140 (stub generation, signature identity, call counts, scope control → WP-GEN-06/07/08) and §6 TOOL-HAR-120 (report unresolved references) cover stub *creation* and *failure to resolve*, but no requirement retains positive resolution evidence or rejects ambiguous object ownership; PLAN-001 WP-GEN-05/06/07/08 descriptions contain no link-map/ownership concept.
- **Assessment:** Ectt plans the same capability surface (stub per external, per-test behavior) but its verification story is negative-only (unresolved reported). The VectorCAST-derived insight — that a successful link does not prove the stub actually replaced the intended object — has no ectt counterpart and would otherwise be silently absent.
- **Recommendation:** Candidate new requirement under §7 STB (e.g. "retain resolution evidence per substituted symbol; reject substitution where ownership is ambiguous") allocated to WP-GEN-05 or a new WP-GEN-xx. Cheap to add now since WP-GEN-05/06 are unimplemented.

### F-03 — "exit(0) without a finalized result record is not a pass" has no ectt counterpart (Class: gap)
- **vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §6: "Do not infer success from process exit code zero. The harness must finalize a result record containing the attempt ID, per-run nonce, selected test revision, completed assertions and artifact identity … Early `exit(0)` without it is abnormal exit." FR-06 lists "premature exit(0)" as a distinguishable case; P09 acceptance: "A test that exits zero before emitting its record is not reported as passing."
- **ectt baseline evidence:** SRS-001 §10 TOOL-EXE-020 (verdicts with expected/actual/location → WP-EXH-01) and TOOL-EXE-060 (non-zero tool exit on failure → WP-CLI-02); SDD-002 §6 S3 has outcomes `pass|fail|error|timeout|not_run` and a `run_id`, but no finalized-record/nonce/protocol-completion semantic; grep for "exit code/exit status/finalize/nonce" across SDD-002/SDD-003 returns nothing; WP-EXH-02 (PLAN line 397) covers segfault/timeout/abort but not premature success.
- **Assessment:** This is the sharpest semantic gap found: ectt's planned result model trusts the framework outcome, and nothing in the baseline defends against a harness killed after exit(0) but before results are written. Risk is highest on Windows (the P15 target), where abrupt termination semantics differ.
- **Recommendation:** Candidate TOOL-EXE requirement (result-record completion gate) allocated to WP-EXH-01/02 before they start; S3 would need a completion marker field. Aligns with the tool's own fail-safe philosophy (TOOL-NFR-090).

### F-04 — Run-attempt model (attempt allocated before build; build-failure as a recorded state) is unspecified in ectt (Class: gap, within an otherwise covered area)
- **vcast-findings evidence:** PRODUCT_ARCHITECTURE.md §3 RunRecord: "Allocate a unique RunAttempt before building, bound to TestRevision and EnvironmentRevision. Attach a BuildAttempt and diagnostics; BuildArtifact is absent until a build succeeds"; execution states include `building`, `build-failed`, `canceled`, `infrastructure-error`. P08.
- **ectt baseline evidence:** SDD-002 §6 S3 outcome enum is `pass|fail|error|timeout|not_run` — no build-failed/canceled state; SDD-002 §11 TestValidationPort returns "build outcome + diagnostics" outside the result set; SRS-001 has no attempt-allocation requirement (closest: TOOL-QUA-060 reproduction info, WP-CORE-04); cancellation is covered by TOOL-NFR-180/WP-CORE-02 but as data validity, not as a recorded run state.
- **Assessment:** Partially covered: timeout/crash distinction is explicitly planned (S3 §6.1, WP-EXH-02). But ectt has no attempt entity, so "attempt recorded before build" and "build failure retained as evidence without fabricating an executable" (FR-03 acceptance) have no home in S3. This matters for provenance (P10) and for FR-12's interrupted-run marking.
- **Recommendation:** Either extend S3 (it is internal per SDD-002 §12 change control, so cheap pre-baseline) with attempt/build-outcome records, or add an SRS requirement for run attempt identity. Decide before WP-EXH-01 starts.

### F-05 — Test "revision" semantics (vcast-findings) conflict with ectt's deliberate stable-identity design (Class: conflict/risk)
- **vcast-findings evidence:** P04: "Store ordered setup actions, typed inputs, expected outputs and test revisions … editing creates a new revision"; PRODUCT_ARCHITECTURE.md §3/§7: TestRevision identities, CompiledTestManifest binding executable case selectors to exact TestRevision ids, "Execution rejects a mismatched test revision."
- **ectt baseline evidence:** SDD-003 §6: "Test case identity is assigned rather than derived from content. A content-derived id would change on every edit, silently breaking coverage attribution, requirement links, and run comparison — the three things that must survive editing (SDD-002 §5.1)"; TOOL-TCD-140 (stable unique id preserved across edits); SDD-003 §7 marks a test *stale* via interface digest (TOOL-CBT-070) rather than versioning it.
- **Assessment:** The two models are reconcilable but not identical: ectt = stable id + staleness digest; the proposal = immutable revisions with attempt-bound execution. Ectt's S3 has a `run_id` but no revision pointer, so "results bound to the exact test revision" (P10, FR-03) cannot currently be expressed. Not a bug — an unbuilt design decision.
- **Recommendation:** When defining S2/S3 concretely (WP-TCM-02), decide whether run records carry a test-content digest (cheap, compatible with both models). A content digest in S3 would satisfy P10/FR-03 without abandoning stable ids.

### F-06 — P15's "validate one Windows host toolchain + real pilot" has no ectt WP, and ectt is Linux-first (Class: gap + scope conflict)
- **vcast-findings evidence:** P15 and §9: validation strategy is "one real pilot project", crash/timeout/cancel "on real Windows", plus §10 equipment baseline (Windows x64, pinned LLVM/Clang). FR acceptance assumes a validated single toolchain before expansion.
- **ectt baseline evidence:** SRS-001 §20 TOOL-NFR-010 "shall run on Linux x86-64" (Must, P1) vs TOOL-NFR-020 Windows/macOS (Should, P2); §17.7 TOOL-UIX-340 Linux+Windows (P2); PLAN-001 WP-TCH-02 (host GCC/Clang), WP-TCH-07 first-run environment verification (TOOL-INS-080, P2), WP-QUA-03 user-executable validation suite (TOOL-QUA-030, P2), WP-SPIKE-03 (Windows packaging install spike). PLAN §5.5 has no pilot/validation-campaign WP; "pilot" appears only in risk register R-4/R-7 narratives.
- **Assessment:** Ectt covers the *mechanisms* (environment verification, validation suite) but assigns them P2 and Linux priority; the vcast-findings posture (single pinned toolchain validated end-to-end before any expansion, on Windows, against a real project) is a different, stronger acceptance gate. Neither SRS-001 nor PLAN-001 contains a "real project acceptance" deliverable — the tool's own §6.4/QUA-03 validation is self-referential.

### F-07 — Coverage completeness semantics live only in SDD-002 S4; SRS-001 has no completeness requirement (Class: risk, surprising b)
- **vcast-findings evidence:** P11: "Missing mapping produces unknown completeness instead of an apparent 100%"; FR-07: "failed TU and missing profile never yield unqualified project-wide 100%"; §3 CoverageSnapshot: "A missing TU mapping means completeness is unknown, not zero coverable entities."
